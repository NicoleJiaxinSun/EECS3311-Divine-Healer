1. Project overview and implementation status
=============================================

The application serves players of an investigation and political story game set in a
healer's estate. Players discover a duplicate labor charge, present evidence to the
steward, request a relief appointment, distribute grain, and correct the official
record. Four events track progress and permit failed endings. Both Java CLI and Swing
desktop interfaces expose the game functions.

The LLM adapter is configured for DeepSeek deepseek-flash through its Chat Completions
API. GameAgent uses model responses to interpret natural-language intent, draft ordered
command proposals, narrate NPC dialogue, and summarize recent history. GameCommand
execution and domain rules determine actual effects. A draft plan changes no world
state. Running requires approval, stops on a refused step, and retries from that step
only after renewed approval.

The submitted scenario implements 12 Stage 1 feature entries. The scenario is
intentionally small, with the steward and healer, a public mill record, a restricted
manor record, 10 starting grain, one relief recipient, and one correction order. These
concrete values and scope choices are documented below. Typed game behavior has been
exercised. Live DeepSeek behavior is unverified because no valid key was available for
the recorded runs.

Build and entry points
  JDK 17 or newer and Maven 3.9 or newer. Run mvn test, mvn compile exec:exec for CLI,
  or mvn compile exec:exec -Dgame.mainClass=estate.GameGUI for Swing.

Local setup
  Copy config.example.json to config.local.json and enter a real key locally.
  DeepSeekAdapter reads LocalConfiguration.apiKey when an AI request is made. A
  nonblank DEEPSEEK_API_KEY environment value takes precedence. The local file and
  .env variants are ignored by Git. Only placeholder configuration is submitted.

3. Implemented design patterns and updated UML
==============================================


Pattern - Command
=================

Design problem
  Game actions must have one execution path across typed UI input, AI proposals, and
  plans.

Participants and roles
  GameCommand is the command interface. InspectCommand, TalkCommand, AllocateCommand,
  and IssueOrderCommand are concrete commands. CommandFactory parses requests into
  Action records. CommandExecutor is the invoker, and GameState, NPC, Inventory, and
  LaborRegister act as domain receivers.

Relevant files and methods
  GameCommand.execute; CommandFactory.parse; CommandExecutor.execute; each concrete
  command's execute method.

Collaboration and benefit
  The factory validates syntax and the executor invokes the command against the
  current domain state. Plans call the same execution path. This centralizes
  invocation and prevents UI code from granting authority or directly deducting stock.

Relationship to Stage 1
  The pattern matches Stage 1. The central GameRules class is replaced by checks
  inside commands and domain operations.


Pattern - Adapter
=================

Design problem
  Provider HTTP details and JSON envelopes must be isolated from interpretation,
  planning, and narration.

Participants and roles
  LLMClient is the target interface, DeepSeekAdapter is the adapter, and the DeepSeek
  Chat Completions API is the external adaptee. GameAgent is the client.

Relevant files and methods
  LLMClient.generate; DeepSeekAdapter.generate; LocalConfiguration.apiKey supports
  local setup.

Collaboration and benefit
  GameAgent passes instructions and context to the interface. The adapter builds the
  request, performs HTTP, checks completion status, parses strict JSON, and maps
  failures to IOException. Fixture clients can verify agent rules through the same
  interface.

Relationship to Stage 1
  The pattern matches Stage 1. The provider and model remain explicit; local JSON
  configuration was added to meet Stage 2 setup requirements.


Pattern - Strategy
==================

Design problem
  NPC cooperation should follow different policies while preserving one negotiation
  entry point.

Participants and roles
  NegotiationStrategy is the strategy interface. NPC is the context. GameState
  constructs two concrete lambda policies, a cooperative healer and a steward who
  requires knowledge of mill evidence.

Relevant files and methods
  NegotiationStrategy.evaluate; NPC.negotiate; policy definitions in GameState.

Collaboration and benefit
  NPC delegates acceptance to its configured policy using an immutable copy of known
  evidence. TalkCommand is independent of the policy details. AI dialogue describes
  the resulting decision after it has been determined.

Relationship to Stage 1
  Stage 1 named CooperativeStrategy and SelfInterestedStrategy classes. The
  implementation uses lambdas through the same interface because these policies are
  short and stateless. This preserves interchangeable decision policies without adding
  empty wrapper classes.


Pattern - State
===============

Design problem
  Only active political events may resolve or fail; completed endings must remain
  fixed.

Participants and roles
  PoliticalEvent is the context and EventState the state interface. LockedState,
  ActiveState, ResolvedState, and FailedState are concrete states implemented as enum
  singletons. EventManager sequences the event contexts.

Relevant files and methods
  PoliticalEvent.activate, handleAction, fail, finished; EventState.activate, resolve,
  fail, finished; EventManager.advance.

Collaboration and benefit
  LockedState permits activation. ActiveState transitions to resolved when its goal
  holds, or failed when abandoned. Terminal states retain themselves and report
  finished. The manager unlocks successors and tests goals without editing state
  internals.

Relationship to Stage 1
  The current implementation matches the Stage 1 state roles. An early enum status map
  was replaced by state objects on November 15; this alignment occurred after the
  stated submission deadline.


Pattern - Observer
==================

Design problem
  Action outcomes must update history and story progress without each command directly
  depending on every consequence service.

Participants and roles
  GameEventListener is the observer interface. EventManager and HistoryRecorder are
  concrete observers. CommandExecutor holds the listener collection and dispatches the
  outcome after each command.

Relevant files and methods
  CommandExecutor.execute; GameEventListener.onGameEvent; EventManager.onGameEvent;
  HistoryRecorder.onGameEvent.

Collaboration and benefit
  The executor sends both accepted and refused results to its listeners. EventManager
  checks only successful results for milestone progress, while HistoryRecorder stores
  both outcomes. Concrete commands remain focused on their domain operation.

Relationship to Stage 1
  Observer matches Stage 1, with one change. The separate PoliticalSystem observer was
  removed and appointment validation now runs in TalkCommand.

All pattern participant names above correspond to .java files under
src/main/java/estate. The repository does not claim persistence itself as a sixth
pattern.

Updated class diagram views

  .puml; CD02C-Events.png and .puml.

Updated use-case and sequence diagrams

4. Changes and rationale
========================

Affected features and use cases
  F01, F09, F11 / UC01, UC09, UC11

Original design
  Separate ActionInterpreter and AgentPlanner with controller-based recap

Implemented change
  GameAgent combines interpretation, planning, narration, and recap; GameSession
  routes both UIs

Reason
  Keep a small application's AI boundary in one service and share routing

Impact on classes, methods, and patterns
  Command and Adapter roles are retained. GameAgent.act, draft, recap, and
  GameSession.run replace the original service entry points.

Affected features and use cases
  F10 / UC10

Original design
  AgentExecutor executes approved plans with a separate AgentPlan

Implemented change
  AgentPlan.run owns execution cursor and lifecycle; it calls GameController.execute

Reason
  Keep approval, pause, retry, and cursor data together

Impact on classes, methods, and patterns
  Command execution is reused. Existing successful steps remain recorded on failure.

Affected features and use cases
  F03 / UC03

Original design
  Concrete named negotiation policies plus optional AI dialogue

Implemented change
  Two NegotiationStrategy lambdas; typed talk and explicit talk-ai operation

Reason
  Small policies need no additional wrapper classes, and explicit narration exposes
  fallback clearly

Impact on classes, methods, and patterns
  Strategy roles remain. NPC.negotiate returns the rule result before
  GameAgent.narrateReview invokes the Adapter.

Affected features and use cases
  F05-F08 / UC05-UC08

Original design
  General resources, official orders, political rank, and four political events

Implemented change
  Grain relief for the mill, one correction order, one role, and four goal-based
  milestones

Reason
  Create a complete playable scenario with inspectable rules and finite outcomes

Impact on classes, methods, and patterns
  This narrows story scope while retaining the original relief, authority, and
  progression needs. Inventory, IssueOrderCommand, TalkCommand.requestAppointment, and
  EventManager implement those choices through Command, Strategy, State, and Observer.

Affected features and use cases
  F06-F08 / UC06-UC08

Original design
  Central GameRules and a separate PoliticalSystem consequence listener

Implemented change
  Local guards in domain commands and appointment in TalkCommand

Reason
  Keep each precondition beside the operation it protects in the present scenario

Impact on classes, methods, and patterns
  No separate GameRules or PoliticalSystem class is submitted. Rule ownership is
  explicitly mapped in Section 2; State and Observer handle event progression.

Affected features and use cases
  F08 / UC08

Original design
  PoliticalEvent plus EventState with four concrete states

Implemented change
  Early status-map implementation replaced by PoliticalEvent and state singletons

Reason
  Align lifecycle ownership with the original State design

Impact on classes, methods, and patterns
  EventManager advances the sequence, while PoliticalEvent delegates transitions. This
  replacement was committed on November 15.

Affected features and use cases
  F11 / UC11

Original design
  Action history with optional recap

Implemented change
  Structured history plus recap of the latest 12 entries; line breaks normalized for
  prose

Reason
  Bound request context and accept ordinary multiline recaps

Impact on classes, methods, and patterns
  HistoryRecorder retains all session actions. GameAgent.recap and displayText
  implement the Adapter call and text normalization.

Affected features and use cases
  F12 / UC12

Original design
  GameStateRepository interface and direct domain save/restore

Implemented change
  Concrete JsonGameStateRepository with versioned command replay and plan snapshots

Reason
  Reuse deterministic command rules when rebuilding a fresh game

Impact on classes, methods, and patterns
  The separate repository interface is omitted. JsonGameStateRepository.load validates
  the full result before GameSession swaps controllers and reconnects GameAgent.

Affected features and use cases
  Shared UI and configuration / supports F01-F12

Original design
  Swing and CLI as alternative interfaces; provider API configuration

Implemented change
  Shared GameSession, background Swing commands, persistent status display,
  config.example.json and ignored config.local.json

Reason
  Keep both interfaces consistent and let a reviewer configure AI without editing
  source

Impact on classes, methods, and patterns
  No new counted feature is claimed. GameSession.run, GameGUI.run,
  DeepSeekAdapter.generate, and LocalConfiguration.apiKey support the existing
  features.
